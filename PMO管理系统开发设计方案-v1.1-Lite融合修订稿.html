00一页纸摘要

轻量版不是简化版完整版的缩写，而是针对当前业务阶段的独立取舍：管理颗粒度只到「里程碑 + 需求」，不建组合、不做资源买卖、不做多层治理机构。

核心判断

当前阶段的 PMO 只需要回答四类问题：这个项目值不值得做？这个方案能不能做成？执行在时间、钱、人天和需求满足上偏离多少？做完后学到什么？系统只收集足够回答这些问题、还原决策和交接工作的数据。

01管理关注点与总体设计

设计从您给出的管理语言出发，而不是从方法论出发。每个关注点直接对应一组可操作的本体结构，中间不经过多余的概念转换。

1.1　五个关注点 → 本体机制映射

产品边界：不依赖聊天平台或第三方表格才能登录；模型停用后，PM 仍能在网页完成全流程。两个入口共享项目编号、对象版本、规则与审计。同一操作是否允许由业务服务决定，不由页面按钮或 Agent 提示词决定。

1.2　项目生命周期状态机

角色与页面（修订建议）：登录后进入“我的项目/待办”。项目工作区分立项和方案、执行台账、周报与证据、评审和复盘。项目成员可在职责内录入；PM 提审并发布周报；评审人独立评分；发起人或指定裁决人签署决定。客户代表确认需求，允许内部人员凭客户书面凭据代录，但必须分别保存签署人和代录人。管理员维护账户和授权，不自动取得业务签批权。

只有一条主链、两个旁路。状态迁移由关口裁决驱动，不允许跳关——这是 8 条规则里最优先保证的一条。

一个务实的简化

不做「实施中期检查」这道关口。项目周期 < 6 个月时，中期检查的形式价值大于治理价值——用三线预警规则替代：出问题随时报，而不是等到中期。这是轻量版与教科书流程的最大差异。

02轻量本体：16 类

以下 16 类沿用原案业务语义。身份、凭据、审计和快照是独立运行所需的支撑数据，不扩充项目治理层级。兼容目标是保留稳定标识，不承诺未来无需数据迁移。

2.1a　两种入口怎样读写同一份数据

建议单体业务服务与关系型数据库起步：浏览器调用 Web API，远程 MCP 适配层将工具调用转换为同一业务命令；二者都不直接写表。证据文件放私有存储。各业务对象使用稳定 ID；记录项目、业务发生时间、录入时间、创建主体及版本。Project.code 唯一；同一项目、期间、报告类型和报告责任人只保留一个当前正式版。跨项目引用拒绝。

基线和评审材料保留版本；决议、状态迁移和审计在同一事务提交。审计区分实际人员、服务身份、代表谁办理、从 Web 还是 MCP 发起。事实一旦采用，不覆盖原文；纠错新增修订记录。删除业务对象采用作废/归档，不破坏历史。当报告来源或权限变化时，引用只向当前有权者展示。

2.2　四个关键结构的字段设计

立项卡、需求、成本、复盘是这套本体里真正每天被使用的四个结构，字段逐条给出，可直接建表。

① 立项卡（Charter）——回答「有没有价值、有没有吸引力」

字段说明必填
valueProp 价值主张一句话：为谁、解决什么问题、凭什么是我们是
targetClient 目标客户/受益方具体到单位与角色，不许写「市场」是
attractiveness 吸引力依据客户付费意愿 / 战略示范效应 / 复购或复制潜力，三选一起，注明证据（已有沟通记录、意向书等）是
expectedBenefit 预期收益定量优先（合同额 / 降本额 / 能力沉淀），定性需说明验证方式是
successCriteria 成功标准结项时如何判定「做成了」——与 Requirement 基线衔接是
roughCost / roughEffort / roughDuration粗估三件套：金额、人天、周期（±50% 精度即可，方案阶段再细化）是
topRisks 主要风险≥1 条，含应对思路（空着不许提交）是

② 需求（Requirement）——质量的唯一载体

字段说明
desc 需求描述一句话可验证的表述，禁止「优化体验」这类不可验证写法
priorityP0（不做则项目失败）/ P1（核心价值）/ P2（可协商）
acceptanceCriteria验收标准：什么条件下算满足。由 PM 与客户代表共同确认后冻结为基线
status基线 → 已交付 → 已验收 → 客户确认；或 取消（须挂 ChangeEntry）

需求满足率公式：满足率 = Σ(已客户确认 × 权重) / Σ(基线需求 × 权重)，权重 P0=3、P1=2、P2=1。取消的需求不算不满足，但计入变更率。

③ 成本（CostEntry）——钱与人天双口径

口径类别示例记录方式
money 金额外采 / 差旅 / 云资源 / 分摊预算（立项或方案阶段）→ 实际（凭发票/付款）→ 预测（剩余部分估算）
effort 人天研发 / 实施 / 管理预算（方案阶段分解）→ 实际（周报填报）→ 预测（PM 估算）

④ 复盘（Lesson 落库前的复盘四问）

  1. 目标对照：立项卡承诺的收益 / 成本 / 周期，实际各是多少？差异主要原因？
  2. 过程表现：三线偏差各发生在哪个阶段？是估算问题、执行问题还是范围问题？
  3. 可复用资产：哪些做法 / 模板 / 方案值得沉淀，下次直接用？
  4. 教训与建议：如果重来一次，立项和方案阶段分别会做什么不同的事？（写入 Lesson，带分类标签）
轻量版最有价值的闭环

教训反哺立项。新项目做立项评审时，PMO 助手自动检索同类历史项目的 Lesson，附在评分卡后面：「过去 3 个类似项目，2 个低估了 X 类人天，1 个因客户确认缺失延期验收」。这一条不需要任何复杂技术，却是完整版也难以替代的价值点。

03三道关口与评分卡

「有价值吗、有吸引力吗、能落地吗」——这三个问题不能靠感觉回答。评分卡的作用不是替人决策，而是把分歧摆到同一个刻度上，并强制留下理由。

3.1　关口①：立项评分卡（价值与吸引力）

共同办理：PM 或其授权智能体可起草同一 Charter，网页核对后由 PM 提交。系统锁定材料版本，助手可读评分与教训、生成材料包；独立评分、复议与最终裁决必须落实到具名人员。建议多人先逐维取均值再加权，任何评审给 1 分即暂停放行、先复议；此汇总口径属新增，须签认。

四个维度、固定权重、每维 1–5 分。评分人独立打分，系统算加权总分；允许异议复议一次，复议记录留痕。

维度权重1 分（典型表现）3 分5 分
战略对齐20% 与任何主线无明确关联 与某条主线相关，但贡献方式牵强 直接支撑明确主线，缺了会有缺口
客户/市场吸引力30% 客户是谁说不清；纯内部设想 有明确客户与真实需求，但付费意愿未验证 客户明确 + 付费/立项意愿已验证 + 有示范或复制效应
财务/资源回报25% 纯投入无回报路径，且人天占用大 回报可期但周期长或不确定 回报明确可量化（合同额 / 降本 / 强制性能力），投入产出清晰
风险可控度25% 关键依赖全部在外部且无承诺 有识别主要风险，应对思路粗略 风险清单完整，每条有应对与触发条件，无单点致命项
加权总分裁决后续动作
≥ 4.2快速立项发起人确认后直接进入方案细化，评审会备案即可
3.2 – 4.2立项通过 + 补强列出低分维度，生成补强任务，方案阶段必须回应
< 3.2不立项 / 重做明确缺失项；一个月内可重报一次，重报须说明变化
任一维 = 1一票否决不论总分——防「三维高分掩盖一维致命伤」
防操纵设计

评分卡最大的风险是被「打人情分」。两条对治：① 每维打分必须选锚点描述（不是拖动条），理由与锚点不符时系统提示；② 分数与实际结项结果事后对照，偏差大的维度在复盘时强制检视——不追责个人，但让「系统性高估」可见。

3.2　关口②：可落地性评分卡（五维短板评审）

与立项卡不同，落地评审不用加权总分，用短板否决：任何一个维度 ≤ 2 分，方案不通过。原因很简单——价值再高，一块短板就能让项目死在半路。

维度检查问题≤2 分的典型表现
技术路径关键实现方案是否清晰？有没有未验证的技术假设？核心环节「再研究」，无备选路径
资源匹配所需人天 / 技能与实际可用人是否对得上？计划依赖「还没招到的人」或关键人 100% 双投
外部依赖依赖方是否已知并给出书面/明确承诺？依赖客户 / 第三方的环节「对方应该没问题」
时间合理性里程碑跨度与工作量是否匹配？缓冲在哪？首尾里程碑挤压全部工作量；零缓冲
验收标准每条需求是否可验收？客户是否确认过基线？验收标准写「按客户满意度」

裁决同样五选一：通过 / 有条件通过（列补强项与期限）/ 暂缓（补材料）/ 调整方向 / 不通过。有条件通过的补强项自动生成 Task，到期未闭环在项目看板上亮黄。

3.3　关口③：结项门槛（三道校验）

裁决与例外：普通结项调用同一检查程序，拒绝时返回缺口及对应对象。原案允许客户书面接受需求偏差，故另设“申请带条件结项”：附未满足清单、原指标、客户签署凭据、整改责任与期限；具名裁决人核对后另立决议。不得把例外写成已满足，也不豁免成本或风险检查。是否允许涉及 P0、谁有权签批待 §9.2 确认；未获授权时保持拦截。

门槛标准不达标时
需求满足P0 需求客户确认率 100%；加权满足率 ≥ 90%不得结项；缺口逐条说明，客户书面接受偏差后方可带条件结项
成本交代金额与人天偏差 ≤ 20%，且超支部分有说明归因补偏差归因（估算 / 执行 / 范围哪一种），直接进复盘议题
无未关闭风险阻塞型风险全部关闭或明确移交运营移交清单 + 接收方确认

04过程三线与 8 条规则

实施期只盯三条线：时间、成本（钱和人天）与质量。提交时同步执行硬拦截；数据更新后计算偏差，每日作业补查缺报、超期与未投递通知。无需独立规则引擎。

线看什么绿黄红

4.2　8 条规则

ID触发条件动作级别
LR-01项目试图跳过任一关口进入下一阶段系统拒绝状态迁移；提示缺哪份评审记录硬
LR-02落地评审任一维 ≤2 分仍申请通过拒绝；生成补强任务清单给 PM硬
LR-03里程碑预测推迟且无对应 ChangeEntry亮黄 + 通知 PM：要么改预测并留痕，要么走变更预警
LR-04成本超 15%（金额或人天任一口径）亮红 + 通知发起人；超 20% 要求重估立项卡（是否继续）预警
LR-05需求范围变动但无 ChangeEntry 记录该需求的验收状态冻结，不计入满足率——杜绝「口头改需求」硬
LR-06连续 2 期无周报，或关键里程碑无任何佐证项目灯标「数据不可信」；三线计算暂停并通知 PM预警
LR-07结项申请不满足 3.3 三道门槛拒绝结项；逐条列出缺口与补救路径硬
LR-08结项后 2 周未完成复盘 / 未沉淀 Lesson项目不能归档；提醒发起人；计入 PMO 月报预警
「硬」与「预警」的区别

计算细则（建议签认）：成本取各口径累计实际加最近一期剩余预测，不累加前几周的剩余预测；金额和人天分别算，成本线取较差灯色。结项按最终实际核对。预算为零或无有效需求时显示“不适用/待补”，不以零或 100% 蒙混过关。获批取消从当前分母移除；LR-05 冻结项建议留在基线分母、不进分子。原案 P0 未确认即红不变。LR-06 优先显示不可信，沿用旧数须标“上次有效”，补证后再算。

处置：预警产生后按项目、规则、对象与本次异常去重，由 PM 或发起人接收、指派、补正，复算恢复后关闭。通知失败重发，不重复写业务。LR-08 满两周发提醒；至少一条已确认教训是归档前置条件，不必等两周才执行。

05证据管道：日报周报

完整版的断言体系在这里压缩成最简形态：报告 → 事实（Fact）。保留溯源与矛盾检测的骨架，去掉置信度公式——用高中低三档替代。

P1
提交 周报固定区块：里程碑 / 人天填报 / 需求进展 / 风险阻塞
P2
抽取 固定区块直读；叙述部分 LLM 按 schema 抽成 Fact，必须带原文引用
P3
比对 新 Fact 与上周同类 Fact 对照：变化进台账，矛盾进澄清队列
P4
汇总 刷新三线 → 跑规则 → 生成项目周报（1 页，PM 确认后发出）

信任三档（替代置信度公式）

人机交接的事实生命周期（补充）：来源报告 → 候选 Fact → 已采纳 / 待澄清 / 已驳回。模式与可信度分开：人工录入不自动算高可信，智能体也不能自行宣布高可信。结构、引文、原报告版本与客观证据均通过才允许按下表采纳；矛盾或低可信进入 PM 待办。例：周报称“12 日已交付”，验收凭证写“14 日”，保留两条来源，澄清后采用有据日期并留理由；不得用后到的文字覆盖前一条。正式周报由 PM 发布，重复抽取同一版本不得重复计入成本或进度。

档判定用途
高有客观佐证：验收记录、付款凭证、客户确认消息、系统数据直接支撑三线计算与结项门槛
中PM 正式填报，无佐证但表述具体（有日期/数字）支撑三线计算；里程碑达成类事实暂计「待佐证」
低口头转述 / 表述含糊（「基本完成」「大概下周」）不参与计算；生成澄清问题返回 PM
对 PM 的回报

填报的固定区块（人天、里程碑预测、需求进展）由系统自动生成周报初稿——PM 核对修改而非从零写。先给省时间的价值，再要数据的质量，这个顺序不能反。

06PMO 助手：单 Agent · 四模式

一个 Agent，按场景切四种模式（同一本体、同一工具集，提示词不同）。不拆多角色——当前规模下多角色带来的协调成本大于收益。

模式何时用做什么禁止做什么
立项评审助理 关口①前 校验立项卡完整性 → 算分并给弱项诊断 → 检索同类项目 Lesson 附历史教训 → 生成评审材料包 不得给出「立/不立」的最终结论，只给建议与依据
过程管家 实施期每日/每周 周报抽取与比对 → 三线计算 → 跑 8 条规则 → 生成项目/组合周报与预警清单 不修改任何基线数据；预警只通知不拦截
结项回顾助理 关口③前后 结项门槛逐条校验 → 生成缺口清单 → 主持复盘四问 → 起草 Lesson 草稿（人确认后入库） Lesson 必须人工确认；不得自动归档项目
台账问答 随时 自然语言查台账：某项目三线？某需求变更史？历史教训？——每条回答带数据时点与出处 查不到就明说；禁止编造（无 Fact 引用则拒答）

6.1　原有五个工具：通过 MCP 调用同一业务服务

工具说明
query_table(filter, fields)按获授权项目、对象和字段查台账、草稿或待办，返回分页记录、版本、时点和出处。只接受白名单条件，不开放任意 SQL。

6.2　共同办理的操作清单（本版补全）

原五工具能查、能算、能写 Fact，但不能保存一份人可以接着编辑的立项卡或周报。本版建议增设三个有边界的业务工具。它们与网页按钮调用同名业务命令，生成的不是聊天记录，而是项目中的正式对象或草稿；不增加第 17 个本体类。

业务动作 / Web 入口MCP 对应操作结果与人机交接
新建立项草稿、编辑周报或教训save_draft：kind 仅 charter / report / lesson；提交白名单字段返回 projectId、objectId、version、draft 状态。新立项由有发起权限的委托人建立 drafting 项目；另两类必须属于已有项目。PM 继续编辑、提审或确认发布。
新建变更申请request_change：目标类型和 ID、目标版本、前后值、理由、证据产生 pending 的 ChangeEntry 和审批待办，不改变原基线。授权人批准时重验版本；批准记录与基线更新同时落库。驳回保留理由。
处理分派任务respond_task：任务 ID、版本、处理说明和证据仅指派给本人或获明确委托的事项可回复，进入“待核验”。责任人核验后关闭；未解决可退回。任务关闭不代替关口批准。
登记事实、查指标、校验关口使用 §6.1 原五工具Fact 进入 §5 的证据流程；计算和校验没有签批副作用。问答不得引入未获权记录。
签署评分、评审裁决、客户确认、批准基线、正式发布、归档不暴露对应 MCP 写工具网页由具名人员核对原件后确认；同样走服务端鉴权与规则校验，不开放直接改 stage 的接口。

6.3　接入契约与失败处理

建议使用独立 HTTPS 端点。Web 会话用于人员登录；MCP 客户端持本服务的有范围令牌，区分个人委托、无人值守服务及客户端身份。授权由服务端取“身份权限 ∩ 项目范围 ∩ 工具权限”；无人值守默认只读，写需点名授权。停用账户或撤销委托后下次调用即拒绝。工具发现与真实调用均按权限处理，证据下载同样鉴权。不得把全部项目原文发给模型。

所有写入带幂等键；改已有对象另带 expectedVersion。相同身份、工具、键与载荷只产生一次业务结果；同键异载荷拒绝。版本冲突不自动覆盖，返回当前版本供重新读取。错误区分未授权、字段缺失、版本冲突、规则拦截；无权对象不泄露详情。响应带 requestId、对象 ID、版本、状态及下一责任人。工具参数、必填字段、返回和错误示例在评审通过后按本清单冻结。

一次实际调用的预期：PM 委托的智能体对周报 R47 提交 save_draft（project=P01，expectedVersion=2，key=K47，新增本周风险说明）→ R47/v3，待 PM 核对。网页打开 v3 修订成 v4；智能体携旧 v3 继续写时得到 VERSION_CONFLICT，重读合并后再提交新键。PM 发布锁定正式版；write_fact 引用该版本，MCP 与 Web 的三线结果引用同一 snapshotId。
