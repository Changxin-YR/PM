# 0012 Fact 出处回执与澄清

依据：主方案 §6、§8.4、§8.6、§17.3、§20.4；T06。此工程决定不授予新业务角色，也不变更 DEC 状态。

- 人工报告作者或有效 PM 可将已实名提交的报告原话提报为候选。Agent 仅在有效 PM 委托、动作和项目显式授权下经同一 REST 写候选。报告详情只为同时持授权的过程管家返回可引用正文；普通报告只读令牌不返回正文。既有报告草稿不可作为 Fact 出处。
- 提报需 `If-Match`、幂等键和当前 `report:{uuid}@{revision}`。服务端重新计算报告哈希，逐字定位正文/结构字符串，保留 JSON Pointer、字符位置、报告 revision、内容哈希和原话。核验时再匹配；相同正文的已提交报告后来发布不破坏旧引用。不能以跨报告的标签作为出处。小数值须用精确字符串；数值须在原话中，不用浮点近似。相同来源的业务重复提报去重，各主体仍分别按自己的幂等键记账。
- 核验由在任 PM 或 Reviewer 完成。中可信必须有现任 PM 的正式报告提交回执和对应的具体数字/日期；高可信需要同一报告的已独立核验附件、实际字节/服务端摘要和核验人记录证据位置与比较依据（对 PDF/图像不假装能自动理解内容）。业务系统保留核验身份和结论，不等同客户或财务签字。
- 同项目、规范化主题/属性、同一 UTC 业务时点存在不同值，相关非驳回记录进入 `disputed`，逐版本记录状态与来源，只产生一个未决澄清和一个 PM 任务；待实际核验并由 PM 明确援引已核验出处后，选择受支持版本，其他候选标为驳回，保留全部历史。任务只能随真实澄清完成。Fact 候选与争议不进入正式三线，不替代任何关口、流水或里程碑的证据。
- 0024 保留旧数据，不按已有 `trust` 回填可信回执。未用该管道生成的旧 Fact 不进入新工作台或自动汇总；若须采纳，重新走提报与核验。

500/版本冲突/非法来源不得部分写入；Fact、澄清、任务、成功审计和 Outbox 同事务。详见 `tests/test_facts.py`、`tests/test_database_roles.py`、`tests/test_recovery.py`。
