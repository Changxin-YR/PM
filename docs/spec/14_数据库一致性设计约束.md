# PMO V1.0.3｜数据库设计与一致性底线

`14_数据库字段类型与约束矩阵.csv` 约束 M0 的字段类型与唯一键设计。**这不是已经执行成功的 Alembic Migration**。M0 必须生成实际 SQLAlchemy 模型、Alembic Up/Down（含真实数据安全检查）并在 PostgreSQL 中完成迁移和回滚演练。

## 必需的数据库级约束

- 通用主键 `UUID`，创建/更新时间使用 `timestamptz` UTC，业务日期使用 `date`；领域主表有 `revision bigint >=1`（乐观锁）。
- Project `UNIQUE(org_id,code)`；Charter `UNIQUE(project_id)`（当前有效版本）；里程碑 `UNIQUE(project_id,ordinal)` 仅对未取消的有效条目建立部分唯一索引；有效个数最多 8 由同事务锁与应用服务维护。
- `project_members` `(project_id, person_id, role)` 唯一且 `assignment_status` 可审计，任命接受必须以真实登录的被邀请人操作；创建者草稿编辑权不需要自动创建 PM 角色。
- CostEntry `actual` 只能服务端从 cost_postings 的 `verified` 有符号明细更新/计算，禁止任何 REST 或 MCP 直接 PATCH；`cost_postings.cost_entry_id` 必须关联同项目、同 type 和同统计 period 的 CostEntry。
- 验证冲销需在行锁/事务内检查 `posting_of_id`，已核验原凭证**至多一条核验通过的全额负向冲销**（部分唯一索引+事务检查）。原凭证、冲销、修正凭证均参与正式求和，不能双减。
- 使用稳定业务凭证指纹避免同一发票/工时凭证通过不同 idempotencyKey 重复核验；对重复来源在核验阶段拒绝或要求独立人工解释（不得自动覆盖）。
- 决策结果 `Decision`、评分卡 `Scorecard`、Fact、健康快照均保留原始版本与源引用；不能因软删除导致引用链断裂。Scorecard `(review_id, reviewer_id, round)` 唯一。
- Reports 同 `(project_id,type,period)` 只能有一个 `current_confirmed=true` 的有效确认版本；允许草稿和历史重报版本保存。
- 规则事件同 `(project_id, rule_id, business_period, fingerprint)` 唯一；通知 Outbox 需去重键，允许重试并避免二次发送。
- `agent_credentials.token_hash` 存摘要而非明文；每次使用同时检查撤销/到期/项目范围/动作范围，Human-only API 不接受 Agent token。
- `audit_logs` 使用独立写权限、追加写入；成功业务事务包含成功审计，拒绝操作通过独立受控事务记录 denied，不复用已回滚事务。

## 核查项目

1. 使用真实 PostgreSQL 对所有 CHECK、UNIQUE、FK 和关键部分唯一索引运行失败用例；不允许只在 SQLite 内存库中验证。
2. 同时模拟两个实例核验同一正向凭证、两个 Agent 同时修改一个 requirement，验证唯一性和乐观锁。
3. 成本凭证插入后重启服务，验证 `actual` 与已核验流水净额一致；手动篡改衍生列应被应用层/数据库权限拒绝。
4. 使用带现有数据的数据库执行升级和失败回滚，检查历史引用和复议记录未被删除。
5. 附件备份与数据库元信息一致，恢复后 `SHA-256` 匹配；不能只恢复一侧。

## 第三轮终审字段矩阵校正（仍需 M0 迁移实现）

- 16 类业务表的通用 `id / created_at / updated_at / created_by / revision` 已逐行列入 `14_数据库字段类型与约束矩阵.csv`，避免主方案要求这些字段而矩阵却漏列；附属表亦增加独立 UUID 主键。**该 CSV 仍不是可执行 SQL 或 Alembic 迁移。**
- `agent_credentials` 显式增加 `org_id` 与 `allow_project_create`，申请时组织范围由被验证的委托人推出而不能由客户端决定；Project 初始化发起者必须是有效人员身份，Agent 不可自动拥有审批角色。
- 通用列必须在实际模型里实现数据库级默认值与 CHECK/UNIQUE/FOREIGN KEY/触发器或等效事务约束，不能把 CSV 中的自由文本标记当作数据库已实施。


## V1.0.4 补充：审计、幂等、Outbox 的可执行契约
- `audit_logs.created_at` NOT NULL，审计 append-only。保留 `org_id/request_id/operation_id/actor_type/actor_id/delegated_by/action/before_hash/after_hash/result/error_code`，至少可确定事件发生时点和操作者。
- `idempotency_keys` 应能返回**首次请求的原 HTTP 状态码和已脱敏响应体**，不能只存 hash；唯一键 `(actor_id,operation,idempotency_key)` 在事务内锁定，并把代理委托身份/组织记入审计。`pending` 状态重入不能重复执行；需要 TTL 及冲突重试策略。
- `outbox_events` 有 `status/next_attempt_at/retry_count/locked_until/last_error`，死信事件可查询并告警；消费端去重，禁止出现“通知成功”但业务事务回滚。
- `agent_credentials` 新建项目时的草稿访问范围与 `projects` 创建事务原子变更；应针对授权增补和 DB 失败回滚单独测试。
- `reports.is_current_confirmed` 与历史 `is_current` 不可混为一义。M0 确定命名/迁移兼容策略，并保证同项目、类型、周期只有一份 current_confirmed；历史版本不可被覆盖。
- CostEntry 预算版本参与三线计算时只能选择**当前获批有效基线**；多个历史版本不得相加。`cost_postings.verified` 仍按有符号净额一次汇总。
