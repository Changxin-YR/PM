# PMO V1.0.3｜领域不变量和真实验收测试清单

> 定位：可直接转换为 pytest / API / 数据库事务测试的规格。`08_静态核验脚本.py` 是独立参考程序，不等于真实产品通过测试。

## 1. 八条规则：不可漂移的判定约束

| 规则 | 程序级条件 | 必须检查的边界/副作用 |
|---|---|---|
| LR-01 | `to_state∈allowed_transitions[from_state] AND gate_passed AND decision_snapshot_current` 才允许迁移 | 非法跳关、合法转移但无 Decision、审批过期、重复提交、业务回滚与拒绝审计 |
| LR-02 | `requested in {pass,conditional_pass}` 且任一有效评审人的任一落地维度 `score≤2` → 拒绝 | 2 拒绝、3 可以评议、补强 Task 幂等生成，禁止用平均分掩盖短板 |
| LR-03 | `forecastDate>currentApprovedPlannedDate` 且无该预警已受控解决记录 → 黄提醒 | 预测推迟 1 天亦触发预警；红时间线不能被黄事件降级；每次变更有原因 |
| LR-04 | `moneyVariance>0.15 OR effortVariance>0.15` → 红提醒；任一 `>0.20` → 继续投入复评待办 | 恰好 15% 不触发 LR04，恰好 20% 不触发重估；预算为 0 而有支出按红异常处理 |
| LR-05 | 受冻结保护字段的非等价变更且不存在合法、已批准、未失效的对应 ChangeEntry → 拒绝 | 恶意字段混入、待审批/错项目/错目标变更不能放行；被拒操作不得提升需求完成率 |
| LR-06 | 连续两个**应交周期**无结构有效的 `submitted/confirmed` 周报，或关键里程碑当期申报进展/完成而无证据 → 不可信 | 历史健康快照不覆盖、外部证据无权限也不算有效、每日规则重跑不重复通知 |
| LR-07 | `closing_ok = (requirement_ok OR valid_requirement_exception) AND money_ok AND effort_ok AND blocking_risks_ok` | 有需求签字但成本超限仍拒绝；需求签字但风险未关闭仍拒绝；无授权签署或签署覆盖范围不足仍拒绝 |
| LR-08 | `closed` 后满 14 自然日仍未完成复盘/确认 Lesson → 提醒；归档要求复盘四问和≥1 confirmed Lesson | 13/14 天边界、已复盘但无 Lesson、重复提醒幂等、终止分支复盘不冒充结项 |

**注意：** 以上固定了测试行为，其中原文没有给出精确粒度的地方属于工程默认值，见 `10_业务决议冻结与未决清单.md`。

## 2. 金额与人天流水的唯一计算法

- `actual = SUM(verified postings signed_amount)`，按 `(project_id,type)` 过滤，不再看投影视图 `reversed` 重新扣除一次。
- `original +100 verified`、`reverse -100 verified` → 净额 0；`original +100 verified`、`reverse -100 verified`、`corrected +70 verified` → 净额 70。
- `original +100 verified`、`reverse -100 pending` → 净额仍为 100。相同原凭证第二次全额冲销、部分冲销、冲销不存在的原记录均不得 verified。
- 正向凭证和反向凭证均不可在核验后被物理改写；冲销核验人不是创建该凭证的行为者/代理委托人。
- `projected_total=actual+forecast_remaining`，`variance=(projected_total-approved_budget)/approved_budget`。正常预算大于零时使用 Decimal，边界比较不按显示格式四舍五入。
- `budget=0` 且有支出为红，`budget=0` 无支出且有正式零预算声明为绿，其余无有效预算为 `untrusted`；不得出现除以 0。

## 3. 条件结项：拒绝“一个布尔变量全豁免”的漏洞

```python
requirement_ok = all_active_p0_customer_confirmed and satisfaction_rate >= Decimal('0.90')
valid_requirement_exception = (
    verified_customer_identity
    and linked_accepted_requirement_ids_cover_all_gaps
    and written_evidence_verified
    and human_authorized_decision_current
    and approval_payload_hash_matches
)
money_ok = money_abs_variance <= Decimal('0.20')
effort_ok = effort_abs_variance <= Decimal('0.20')
risk_ok = all_blockers_closed_or_formally_transferred
closing_ok = (requirement_ok or valid_requirement_exception) and money_ok and effort_ok and risk_ok
```

对任意例外必须先检查书面接受的具体需求 ID，不能信任由 Agent/客户端发来的 `signedException=true`。一份真实的需求偏差接受函**不构成**额外成本或未关闭风险的批准。

## 4. 身份、草稿与职责任命

- 有效认证成员创建 `drafting` 草稿后，即获得自己草稿的编辑权；同角色其他成员不能编辑其草稿；发起人不自动成为 PM 或 Reviewer。
- 发送 Sponsor/PM 任命邀请只能由有权人办理；Sponsor/PM 本人通过独立 Web 会话接受才算 `accepted`；Agent 无法使用 token 代人接受。
- 送立项评审前双角色已接受、Charter 必填、风险≥1；少任何条件不得迁移。
- 关口最终裁决/客户确认/凭证核验/正式归档均需人类身份独立授权；MCP 工具无相关方法还不够，直接 REST 调用也应 403。
- 评审人不得批准自己的申请；审批请求的内容哈希、实体 revision 和源证据在真正执行前重新核验。

## 5. 审计与事务

```text
成功写入：鉴权→校验→业务事务(实体/Decision/Outbox/成功审计)→commit
失败写入：鉴权→校验失败→业务事务rollback→受控的独立 denied 审计→4xx
```

两条路径均保留 requestId。被拒绝操作**不能写入成功审计**，也不能因 denied 审计写入失败而悄悄继续执行。M0/M2 必须测试数据库故障注入下的事务回滚、审计失败和 Outbox 重试。

## 6. 从规格到真实软件验收的最低要求

| 测试组 | 最低要求 | 最终证据 |
|---|---|---|
| UNIT | 四维评分、五维短板、三线、LR01～08 及全部参考向量 | pytest 运行日志 + 覆盖报告 |
| DB | 关键 FK/唯一键、并发旧 revision 409、反向凭证唯一约束、非法迁移无业务写入 | PostgreSQL 集成测试和迁移日志 |
| REST | 项目 Owner、角色邀请、评分与审批、客户确认、结项例外 HTTP 拦截 | FastAPI 测试客户端 + OpenAPI 校验 |
| MCP | 每个注册工具 inputSchema、授权范围、直接 HTTP 禁权、客户端真实 Host | MCP stdio 和目标 Host 实际会话记录 |
| E2E | 人工通过 Web 创建→方案→三关口→结项→复盘归档 | Playwright 脚本及屏幕/日志证据 |
| AI | 四模式输出校验、事实出处、注入和模型失败不影响人工作业 | 模型/禁用模型双轨测试 |
| OPS | 启动、迁移、备份/恢复、调度补跑不重复发出 | 空白环境复现命令与退出码 |

**所有正式指标必须带 `asOf`、`ruleVersion`、`sourceRefs`、输入快照；数据不可信时返回 `untrusted`，旧快照只作历史展示。**

## 7. 第三轮终审新增反向测试

- 新建草稿的 MCP Token 带 `allowProjectCreate=true`、发起人有效且组织范围匹配时，创建成功但不自动获得 Sponsor/PM/Reviewer 身份。
- 任一条件（委托人停用、组织不匹配、未授予 `pmo_project_create` 动作、`allowProjectCreate=false`）时，直接调用 REST `POST /projects` 也必须 `403`，不能只在 MCP 本地适配器检查。
- 附件上传必须实际携带 `multipart/form-data` 文件字节，校验 MIME/大小/隔离存储，后端计算 SHA-256；上传人提供伪造 hash 不能让文件被判为已核验。
- 评分维度提交必须包含 score、对应锚点码、理由和合法证据引用；评分 2 携 `score_5`、评分维度与 Review 类型不匹配均需 `422`。
- 实测 Web 完成里程碑，报告草稿提交与分析、待任命接受、账户管理和令牌撤销操作，逐项与 OpenAPI baseline 的 opId 对照；不允许 UI 按钮无对应后端服务。


## 8. V1.0.4 新增 P0 运行测试
- **幂等原响应重放**：同 actor+operation+key+payload，数据库仅发生一次写入；重试返回首次 HTTP 状态、业务 ID 与等价业务响应体，不以 responseHash 冒充原响应。不同 payload 同 key 返回 409；并发处于 processing 时不能双写。
- **Outbox 故障恢复**：业务提交后模拟投递失败、重启、超时租约恢复、退避重试、死信和重复消费；消息最多一次的业务副作用由去重保证。
- **安全审计时间线**：拒绝操作必须有 `created_at/request_id/actor_type/actor_id`，业务 rollback 不残留假成功日志；审计写入失败不得放行高风险请求。
- **Agent 创建后闭环**：同令牌创建项目后可以改本人草稿、立项卡、预算/需求/里程碑草稿；无法获得 PM/Sponsor/Reviewer，不能访问其他项目；授权增补和项目创建必须原子提交。
- **路由级事务**：人工 Reviewer 对通过关口的 `POST /reviews/{id}/decisions` 必须原子改变项目状态；注入中途故障时 Decision、状态、成功审计、Outbox 要么全成要么全不成。
- **预算历史隔离**：存在两个预算版本时只取当前已批准版本；凭证金额只按全部已核验正负流水求和一次。
- **终止分支**：`terminated→retrospective` 为终止复盘，不得被错误应用正常结项的 LR-07；归档仍要求 Lesson 人工确认。
