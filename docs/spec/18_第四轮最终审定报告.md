## 2. 本轮实际修复的问题

| 编号 | 严重度 | V1.0.3 的缺口 | V1.0.4 处理 |
|---|---|---|---|
| F-01 | P0 | `audit_logs` 缺少明确 `created_at` | DB 字典加入事件时间、请求/操作者/错误关联；审计定义 append-only |
| F-02 | P0 | 幂等表只存 `response_hash`，不能原响应重放 | 增加 `response_body/response_status/status/created_at/expires_at/actor_type`，明确同键同入参返回原响应 |
| F-03 | P0 | Outbox 缺租约/尝试/重试/死信数据 | 增加 `status/retry_count/next_attempt_at/locked_until/last_error` 和消费去重契约 |
| F-04 | P0 | Agent 新建项目成功后令牌权限可能不含新 ID，导致后续草稿修改失败 | 定义组织级创建授权，在同一事务把新项目的**仅草稿权限**纳入原 Token，禁止角色提升 |
| F-05 | P0 | Gate 决议 API、状态迁移 API 存在事务/入口语义歧义 | 明确唯一领域服务 `transition_project()`；人类最终决议与迁移/审计/Outbox 同事务 |
| F-06 | P1 | 通用路由要求 `reviewer`，但暂停/恢复/终止等需要 Sponsor/PM 权限 | 补逐迁移角色矩阵，不以一个角色替代全部业务场景 |
| F-07 | P1 | `finance_verifier` 看似出现未定义新 PMO 角色 | 定义为受组织显式授予的操作能力；系统管理员不自动拥有审批权 |
| F-08 | P1 | 40个MCP `outputSchema.data` 都仅是自由对象 | 每项补**最小封闭 typed DTO**，静态校验含必填与额外字段拒绝；仍需真实SDK测试 |
| F-09 | P1 | `Person.role` 被误用为角色授权的风险 | 明确仅为描述字段，正式鉴权以 user_roles/project_members/允许动作解析 |
| F-10 | P1 | 报告当前确认版本、预算版本不够清晰 | 新增报告/预算版本字段，要求当前有效版本唯一，历史版本只用于追溯 |
| F-11 | P1 | 一般 `CostEntry` 历史预算和现行预算可能重复汇总 | 预算版本选择约束，按当前已批准基线计算，初始基线仍保留 |
| F-12 | P1 | 规格检查不能验证输出 DTO 有真正约束 | 新增 `19_最终加固核验.py`，对40份结果做有效样例+3类负向变异检测 |
| F-13 | P1 | 原文 §2要求每个类有明确 Owner，未落实清单 | 在主方案 §20.2 增加16类 Owner 与责任主体矩阵 |
| F-14 | P1 | Codex 可自由修工程但审批/业务未决边界不够明确 | 新增一份完整自主开发主提示词，分可自主/保守/严禁和阶段证据 |
| F-15 | P2 | API 比率和资金数值的 JSON 表现易造成浮点差异 | 统一权威 Decimal，序列化使用十进制字符串，前端只做展示 |

以上属于**工程稳定性和可执行性修复**。没有更改原始三关口、八规则的阈值及权重。因本轮没有改变业务政策，**规则版本仍为** `lite-v1.0-standalone.3`，开发规格版本提升为 `PMO-Standalone-1.0.4`。
